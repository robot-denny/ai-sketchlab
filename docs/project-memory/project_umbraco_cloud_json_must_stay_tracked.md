`src/UmbracoProject/umbraco-cloud.json` MUST remain git-tracked on Umbraco Cloud — do NOT `.gitignore` or `git rm --cached` it, even though it contains secrets (`Deploy.Settings.ApiKey` + `Identity.ClientSecret` + the project `Workspaces` list). Confirmed by Umbraco support 2026-07-09. Untracking it broke the CI/CD build (the artifact build needs the file in git) AND Dev boot.

**KEY MECHANIC — the deploy PATH decides whether git content reaches an env's copy.** Two surfaces:
- **CI/CD Flow path (GitHub Actions → Cloud CI/CD Flow API).** With `skipPreserveUmbracoCloudJson=false` (default), the git-tracked file is NOT deployed over an env's own copy — each Cloud env keeps its own file (its own workspace + `Identity.EnvironmentId`). Via this path you canNOT fix a broken env file by pushing git content, and a Portal restart just regenerates it. **Caveat that caused the Jul-9 outage:** preservation protects an *existing* env file's content, but if the git copy is **deleted**, that deletion propagates and strips the env's file (→ "Deploy ApiKey is not configured"); and if the env copy is already gone, the next deploy lands the git content verbatim (a Live-only git copy → boot crash `Unable to determine environment by its id …`, because the env's runtime env-id must be in the file's `Workspaces`).
- **Direct SCM push (git push to the env's own Cloud SCM remote, e.g. `dev-cloud`).** Writes the environment's OWN git repo, so content DOES land in that env's copy — the recovery lever. **Confirmed 2026-07-10: a direct FF push of the corrected all-workspaces file to `dev-cloud/master` wrote Dev's own copy and brought Dev back up, no support ticket.** Branch off `dev-cloud/master`, apply only `umbraco-cloud.json`, **FF push — never force-push** (SCM master has 100+ Cloud auto-commits); the push runs Cloud's deploy synchronously so it "times out" at ~2min but has landed (verify `git ls-remote dev-cloud master`). See [[project_git_push_to_github_not_origin]] for why this remote is normally off-limits — this is the deliberate exception when the CI/CD pipeline itself is down.

**Topology decision (2026-07-28) — keep the tracked file STOCK all-workspaces (Dev+Live); do NOT re-introduce a Live-only divergence.** The only reason anyone kept a Live-only `Workspaces` was to force local's Deploy transfer target to be Live directly (old "author locally → push to Live"). That workflow was retired — content now flows **local → Dev → Live** through the pipeline ([[project_content_authoring_direction]]), and the stock all-workspaces file makes local's next hop Dev (the local dashboard shows "Transfer to Dev"; Deploy always transfers to the immediately-next env, no skipping). Reverting to Live-only would fight the new content direction AND re-arm the Jul-9 deletion landmine. The all-workspaces requirement strictly applies to each **env's own copy**; the git-tracked copy only needs to exist, but keeping it stock all-workspaces avoids the crash-on-relanding hazard.

**How to apply:** (1) never untrack — stays git-tracked AND stock all-workspaces (Dev+Live), no Live-only divergence in the working tree. (2) If CI/CD is down because of this file, recovery = re-track + **direct FF push to the affected env's Cloud SCM remote** (writes the env's own copy), NOT the GitHub Actions path (which preserves it). (3) A genuinely corrupt env file with no git-content cause may still need Umbraco support. (4) Secure storage of the embedded secrets on a public repo is an OPEN follow-up — interim: private repo + rotate Identity ClientSecret. Unrelated to search-index corruption — see [[project_gate2_transient_deploy_flakiness]].
